# pipeline-replay-viz

Reading the code of a pipeline tells you what each stage *should* do; only replaying real
records through it tells you what it *does* — and a picture of that replay is what makes
the behavior obvious to someone else. The method has three parts that must stay honest:
**a bench that reproduces production**, **verdicts against a ground truth the pipeline did
not produce**, and **visuals whose every number comes from real data or is labelled as
derived**.

## 1. A bench that replays from zero

- **Capture real inputs at the source boundary** (raw messages as they entered, with their
  original timestamps and keys), for a bounded period and a handful of entities. Keep them
  out of any repo (they are production data); store per entity/day so a capture can resume
  and widen.
- **Reset everything stateful between runs**: input topics, stream-processor state
  (changelogs, local state dirs, committed offsets), and the destination rows of the
  entities under test. A run that starts on yesterday's state is not a run.
- **Prove the bench reproduces production first**: replay with the production code and
  compare the stored rows / final objects with production's (counts + a content hash per
  entity, then row by row). Only a bench that matches prod can judge a fix. Explain every
  residual difference before moving on (e.g. a filter whose state prod loses on restarts).
- **One run per code version, named by what it adds** (A = prod, B = +fix 1, …), each
  snapshotted the same way: stored rows, final objects from the *real* service code
  (call it, don't reimplement it), and a meta file with branches/commits/dirty flags.
- **Wait for "really done"**: lag 0 on every consumer *with active members* — a group with
  no members reports no lag and fakes completion; also watch the processor's own logs for
  a stopped stream (an app can stay "up" with a dead stream thread).

## 2. Ground truth from the source, then verdicts

- **Look for the structure the source already provides** before trusting the one the
  pipeline rebuilds. Devices and vendor APIs often carry their own session/transaction ids,
  start/end events or counters that downstream code ignores and then tries to infer.
- **Rebuild the source-side truth** (sessions, totals) from raw records only, and an
  independent measure when available (e.g. an energy/odometer counter vs a computed delta).
- **Compare final objects to that truth with explicit, numeric thresholds** (start/end
  shift, start/end value, total vs independent measure), match by largest overlap, and
  glue artificial splits (day boundaries, pagination) before comparing.
- **Verdicts carry a reason**: conforme / cut / start value lost / ended early / absent /
  split by the source itself / merged. Count them per run: the before→after delta is the
  headline. Separate *observed* from *inferred*; never let a comparator artefact pass as a
  pipeline defect (check suspicious verdicts on the raw records).

## 3. The two visuals

Both are generated by a **stdlib-only Python script** that reads the captures and run
snapshots and writes **one self-contained offline HTML** (hand-built SVG + vanilla JS, data
inlined). No CDN: corporate networks block them, and a single file can be attached to a
ticket. Re-run the script after each new run.

- **Before/after explorer** — `references/explorer.md`: entity and day pickers with badges,
  one shared time axis for source lanes, then a BEFORE block and an AFTER block (stored rows
  + final objects), per-item comparison cards with verdict and reason, period summary,
  explanations drawer, keyboard and URL-hash state.
- **The machine** — `references/machine.md`: the pipeline drawn as stations; a real record
  enters, is split/filtered/transformed, merged into a stored row, read by the service, and
  becomes a final object; deterministic seekable timeline with slow motion; intermediate
  messages are *recomputed* from inputs and checked against the real stored rows
  ("fidèle aux données réelles ✓" badge); downstream logic is a port validated against the
  real final objects; didactic simplifications are stated on the page.

Pick 3–5 **excerpts** that each show one mechanism (a cut, a lost value, a bounce, a
filtered duplicate), with a "what to watch" caption and timed notes, in BEFORE and AFTER.

## 4. Verify before showing

`references/verification.md`: headless Chrome renders at several states, console capture
(first prove an error *is* captured), screenshots inspected for overlaps and empty charts,
reduced-motion and dark mode checked. Report what was verified, what is approximated, and
any mismatch the fidelity check found.

## Pitfalls seen in practice

- **"Changes only" deduplication filters** (emit a value only when it differs from the last
  one) silently change the meaning of a missing value from "unknown" to "unchanged". A
  downstream consumer that needs a value *at a given instant* (start of a session) or that
  closes a state when a row lacks a flag breaks. Their in-memory state is usually lost on
  restart, so production sometimes *hides* the bug that a clean replay exposes. Know the
  exact semantics (last value seen incl. dropped ones? late records forwarded?) — replay
  order matters for stateful filters.
- **State carried only on change** (a cable/flag sent on transitions) vs a consumer that
  expects it on every row: fix upstream by re-asserting the state on each relevant record
  when the source gives a reliable marker (a session id on in-session messages only —
  some unrelated messages keep a stale id for a while after the session ends: filter by
  message type).
- **Physical bounces and arrival messages**: connect/disconnect/connect within ms, or an
  "end of trip" message 30 ms after a plug-in — tolerate a short settling window.
- **Day splits** that copy state into the next day's piece (inventing an activity or sharing
  one period object between two meanings).
- **Time zones**: store UTC, show local, label which one every timestamp is in.
- **Size**: keep the HTML to a few MB (aggregate, cap points, collapse idle gaps).
